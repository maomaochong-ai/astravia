# im-gateway 活动回合消息折叠：以「是否已答复」而非时间间隔聚合连发消息

IM 用户（尤其微信）习惯把一个需求拆成几条短消息连发。现状 im-gateway 的 [[router]] 按 `(userID, chatID)` 串行处理：**每条消息 = 一次 `Send(prompt)` = 一轮 agent = 一组回复**——连发三条就得到三轮、三组回复，体感像在跟三个机器人说话；用户中途想纠偏（「等下，用 Python」）也只能等当前轮跑完再另起一轮。目标是让连发消息聚合成一轮、只产出一组回复，并允许「只要 agent 还没给出答复就一直能打断补充」。

最初的直觉方案是**时间防抖**（连续消息间隔 < T 就合并）。但时间间隔无法区分「用户分多条说同一需求 / 中途纠偏」与「另起一个新需求」——快慢都可能是同一意图，也都可能是新意图。

## 决定

引入 [[活动回合]] 状态机与 [[消息折叠]] 策略，判据**只看「本回合是否已答复」、完全不依赖时间间隔**。

每个会话 `(userID, chatID)` 维护回合状态：

- `IDLE` → 来消息 → 该消息当种子，启动 `forwardToAgent`（进入 `ACQUIRING`）
- `ACQUIRING`（host session 冷启动、prompt 尚未发出）→ 来的消息**并入种子 prompt**
- prompt 发出 → `RUNNING`
- `RUNNING` → 来消息 → 走 coding-agent RPC 现成的 `steer` 命令**注入**正在跑的 agent，agent 在下一个工具边界重新规划并纳入新消息
- `agent_end`（最终答复「落定」）→ 回到 `IDLE`；其后到达的消息才另起新回合

「已答复」在飞书 / 微信统一以 `agent_end` 为界：飞书流式打字途中、微信 [[DeferUntilTurnEnd|im-gateway inbox]] 整轮期间都属于活动回合、都可被折叠。活动回合期间的消息**一律 steer，不再过 slash 命令解析**；命令只在 `IDLE` 生效。无「硬取消」出口——纠偏即发消息。

router 实现需把 `bridge.Run` 从「阻塞队列消费」改为独立 goroutine，会话循环 `select{ 入站队列, bridge 完成 }`：`RUNNING` 期间从队列取到消息就经 `acq.Session` 发 steer 命令；bridge 返回（`agent_end`）即回合结束、`Release`、回到 `IDLE`。

## 关键取舍

**为何 turn-state 而非时间防抖。** 时间间隔是错误的信号——它度量的是「打字快慢」，而我们真正要区分的是「同一意图的延续 vs 新意图」，后者恰好由「agent 是否已交付答复」精确刻画。turn-state 还天然消除了「防抖窗口该设多长」这个无解的调参问题。

**为何 steer 而非 abort 重跑。** 二者都无法回收已执行的副作用（写文件 / 已发附件），但 steer 保留 agent 已做的工作（已读取的结果、已规划的步骤），由 agent 自行在下一步纳入新消息；abort 重跑则冷启动丢弃一切、更慢。coding-agent RPC 已内建 steer，gateway 只需接线。

**为何不加启动防抖定时器。** `closeOnIdle` 冷启动的 `Acquire` 延迟（~1-2s）本身就是个免费合并窗：用户连发的后续消息常恰好落在 prompt 发出前，自然并入种子 prompt。零定时器 = 单条消息零额外延迟，符合「不靠时间」的判据。代价：Acquire 偶尔过快时 agent 会对半截需求先反应一下、随即被 steer 纠正（微信 defer 下不可见；飞书可能闪一下）。

**为何活动期一律 steer、不过命令解析。** 命令的单独回复会破坏「一轮一回复」；活动回合内用户的任何输入都应被理解为对当前任务的补充/纠偏，交给 agent 自行消化最简单，也契合「一直能打断补充」的心智。

## 后续若改变主意

- 若 Acquire 过快导致飞书「闪一下」体验不可接受，再叠加一个**仅作用于回合开始**的小静默窗（不退回全程时间防抖）；
- 若用户需要「算了别答了」的硬取消，作为独立手势（如 `/stop` → abort 整轮且不回复）正向加回，而非改动折叠主线；
- 若多条快速 steer 需要去抖/批量，在 RUNNING 分支内按需聚合，不影响状态机骨架。
